# Conventions

The standing rules of `formal/`, for adding validators and for future work.
The recipes rely on the rules marked (enforced), and fail with a message when one does not hold.

## Layout

- Validator-independent Lean is in `Formal/Universal/`.
  `Formal/Common.lean` is the one exception, still to be decided.
- Each validator has a folder under `Formal/`, such as `Formal/Vesting/Linear/` (enforced).
  Its hand-written proofs are the files in that folder, imported by `<folder>.lean`, such as `Formal/Vesting/Linear.lean`.
  `Formal.lean` imports every one of these.
- Each validator's universal checks are in `<folder>/Blueprint/` (enforced).
- `Formal/` holds only `.lean` files.
  The one exception is a module's `properties.json`, which the property-catalogue scripts read from there.
- The documentation of `Formal/X` is in `docs/X`, such as `docs/Vesting/Linear/README.md`.
  `docs/` is temporary: it moves to the repository's `docs/` later.
- The logs of `Formal/X` are in `logs/X`, such as `logs/Vesting/Linear/doubleSatisfaction.log`, and are not committed.
- Tooling is in `scripts/`; Python's `__pycache__/` is not committed.

## Generated and hand-written files

| File | Written by | Committed |
|---|---|---|
| `Blueprint/Tx.lean` | the validator's author; generated once as a skeleton, never replaced | yes |
| `Blueprint/Types.lean` | the generator, on every run | to decide |
| `Blueprint/Checks.lean` | the generator, on every run | to decide |
| `Scripts/<module>.<validator>.cbor` | the recipes, copied from the blueprint | no |

Nothing imports the `Blueprint/` files, so `lake build` does not check them.
Generated files start with "Generated by process_blueprint.py … Do not edit".

## Validators and recipes

- Every validator comes from `../onchain/plutus.json`; the sale example is the one exception, with its own path in its recipe.
- Every validator has one recipe in the `justfile`, naming its folder and its name in the blueprint.
  When it has hand-written proofs, it is also listed in `proved`, which `just verify` uses.
- Before anything reads a validator's compiled code, `aiken build` runs and the code is copied to `Scripts/` (enforced).
- A recipe's argument chooses what runs (enforced):
  - none: the validator's hand-written proofs;
  - a name starting lower-case, such as `doubleSatisfaction`: that universal check, with `someAccepted`;
  - a name starting upper-case, such as `Soundness`: that file of the hand-written proofs.
- One run is one universal check, stopped after 5 minutes.
- With Nix, any recipe runs as `nix develop --command just <recipe>`.

To add a validator:

1. Add its recipe to the `justfile`.
2. Run `just <recipe> someAccepted`: it writes `Blueprint/Tx.lean` as a skeleton and stops.
3. Write one shape per action in `Tx.lean`, following the rules below.
4. Run `just <recipe> someAccepted` until it holds, then the other checks, one at a time.

## Names

- Checks are called by name only; numbers appear only in `docs/Universal/PROPERTIES.md`, which also lists the former IDs.
- A check's theorems are named `<check>_<shape>[_<variant>][_applies]`, such as `doubleSatisfaction_buy_applies`.
  For `otherPurpose` and `malformedRedeemer`, the purpose takes the place of the shape.
- A shape is named after its action, lower-cased first, such as `buy`; its leaves are the structure `BuyLeaves`.
- Checks are ordered by the part of the transaction they change, and within a section, those that must reject come before those that must still accept.

## Writing shapes

- A shape fixes the structure of the transaction; every other value is a leaf.
- List lengths are structure: never symbolic.
- Every amount, key, time and hash is a leaf, unless a recorded limitation requires a literal.
- Currency symbols are literals, defined once as a constant (`DEAD_ENDS.md` §17).
- Signatories are independent leaves, such as `[p.s1, p.s2]`, not roles tied to positions.
- Leaves are not shared unless the transaction requires it: a separate payee and signer cover more than one shared key.
- Inputs are sorted by reference, as the ledger model requires.
- Spends are built with `Spend.context { … }`, every input and output named with `let`.
  A part that `Spend` fixes, such as an empty mint, is opened by updating the built context in `Tx.lean`.
  `Formal/Universal/TxBuilder.lean` is shared by every validator and is not changed for one of them.
- Each part of the transaction gets one question: does the validator read it?
  If not, leave it at its default; if so, make it a leaf, or write a second shape for each form it can take.

## Writing checks and helpers

- No symbolic positions in lists (`eraseIdx i`, `set i`, `i ∈ positions`): they stall Blaster (`DEAD_ENDS.md` §19).
  Act on the first element, and check order independence separately.
- Boolean tests (`contains k = false`, `Option.any`) rather than membership (`∉`) or other inductive propositions.
- No arithmetic over values of unknown size (`Value.add`); append a fixed entry instead.
- Every check on a change has an `_applies` partner, so that a pass cannot be vacuous.
- A check is general and free of intent: anything that needs the contract's intent belongs in the hand-written proofs.

## Documentation

- Markdown with one sentence per line.
- Literal language, one name per concept, terms defined before use, problems stated before solutions.
- Failed approaches are recorded in `docs/Universal/DEAD_ENDS.md`, with what was tried and why it failed.
- Results of the universal checks are recorded in the results table of `docs/Universal/PROPERTIES.md`.
